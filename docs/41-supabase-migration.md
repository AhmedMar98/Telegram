# ترحيل القاعدة إلى Supabase — الدليل التنفيذي

**القرار:** Supabase (سنغافورة) — قرار المالك، يُلغي توصية `docs/14-postgres-alternatives.md` بـNeon.

**لماذا الآن:** قاعدة Render المجانية تُحذف بعد ٣٠ يوماً من إنشائها. هذه ليست
مخاطرة محتملة بل حدث مؤكَّد بموعد.

---

## ١. ما جهّزه الكود فعلاً، وما يحتاج يدك أنت

| البند | الحالة |
|---|---|
| `normalize_database_url` يقبل روابط Supabase Pooler | ✅ **مُتحقَّق منه بالتشغيل** — منفذا 5432 و6543 كلاهما يتحوّل إلى `postgresql+psycopg://` صحيحاً |
| أداة التحقّق من اكتمال النقل | ✅ `scripts/verify_migration.py` — مكتوبة ومُختبَرة بعشرة اختبارات |
| إنشاء مشروع Supabase | ⛔ **أنت** — يتطلّب حساباً واعتمادات |
| تنفيذ النقل الفعلي | ⛔ **أنت** — يتطلّب كلمة سر القاعدة، ولا تُكتب في محادثة |
| قلب `render.yaml` | ⛔ **عند القطع فقط** — راجع الفخّ في §٣ |

---

## ٢. الفخّ الذي يجب معرفته قبل البدء

`render.yaml` يحقن `DATABASE_URL` تلقائياً من قاعدة Render:

```yaml
      - key: DATABASE_URL
        fromDatabase:
          name: link-intel-db
          property: connectionString
```

**لا تحذف كتلة `databases:` ولا تغيّر هذا السطر قبل أن تضبط `DATABASE_URL`
يدوياً في لوحة Render.** لو فعلت، أول إعادة نشر ستجد الخدمة بلا رابط قاعدة
إطلاقاً — لا تُقلع، والموقع يسقط. الترتيب في §٣ مصمَّم لتجنّب هذه اللحظة
تحديداً.

---

## ٣. الخطوات بالترتيب — كل خطوة قابلة للتراجع قبل التي بعدها

### الخطوة ١ — نسخة احتياطية أولاً، قبل أي شيء

```bash
pg_dump "$OLD_DATABASE_URL" --no-owner --no-privileges -F c -f pre-migration.dump
```

احتفظ بها خارج المستودع. **لا تكمل قبل أن تتأكد أن الملف موجود وحجمه معقول.**

### الخطوة ٢ — أنشئ مشروع Supabase

- المنطقة: **Southeast Asia (Singapore)** — الأقرب للخليج بين المتاح مجاناً.
- خذ رابط الاتصال من: Project Settings ← Database ← Connection string ←
  **Session pooler**.

> **لماذا Session pooler إلزامي:** الاتصال المباشر بـSupabase يعمل على IPv6
> فقط، وGitHub Actions وRender لا يوفّران IPv6 صادراً. الاتصال المباشر
> سيفشل بأخطاء شبكة غامضة يصعب تشخيصها. الـPooler يعمل على IPv4.

### الخطوة ٣ — ابنِ المخطط بالترحيلات، لا باستعادة عمياء

```bash
DATABASE_URL="<supabase-url>" python -m alembic upgrade head
DATABASE_URL="<supabase-url>" python -m alembic check
```

بناء المخطط من الترحيلات (لا من `pg_restore` الكامل) يضمن أن `alembic_version`
صحيح على القاعدة الجديدة، وأن أي ترحيل مستقبلي يعمل.

### الخطوة ٤ — انقل البيانات فقط

```bash
pg_restore --data-only --disable-triggers \
  -d "<supabase-url>" pre-migration.dump
```

`pg_restore` **يخرج بالرمز 0 حتى لو تخطّى صفوفاً** — لهذا الخطوة التالية ليست
اختيارية.

### الخطوة ٥ — تحقّق أن كل صفّ وصل (لا تتخطّ هذه)

```bash
SOURCE_DATABASE_URL="<render-url>" \
TARGET_DATABASE_URL="<supabase-url>" \
python scripts/verify_migration.py
```

- رمز خروج **0** ورسالة `Verified: N tables, M rows` = النقل مكتمل.
- رمز خروج **1** = فرق موجود، والأداة تسمّي كل جدول ناقص بالعدد بالضبط.
  **لا تكمل. لا تُحِل قاعدة Render للتقاعد.** أعد الخطوة ٤ للجداول المتأثّرة.

### الخطوة ٦ — تحقّق أن عزل الصفوف (RLS) ما زال فعّالاً

```bash
DATABASE_URL="<supabase-url>" python scripts/check_setup.py
```

ابحث عن سطر `row-level security`. **يجب أن يقول `enforced`.**

> **تحذير حقيقي:** المزوّدون المُدارون كثيراً ما يعطونك دوراً بصلاحية
> `superuser`، وSUPERUSER **يتجاوز RLS كلياً** — السياسات تبقى موجودة ولا
> تحمي شيئاً. لو ظهر `superuser_bypasses_rls`، أنشئ دوراً عادياً في Supabase
> واستخدمه في `DATABASE_URL` بدل الدور الافتراضي.

### الخطوة ٧ — القطع (هنا فقط تلمس `render.yaml`)

بالترتيب حرفياً:

1. في لوحة Render: أضف `DATABASE_URL` **يدوياً** بقيمة رابط Supabase.
2. تأكّد أن الخدمة أقلعت وتعمل على القاعدة الجديدة.
3. حدّث أسرار GitHub Actions: `DATABASE_URL` في المستودع.
4. **ثم** عدّل `render.yaml`: احذف كتلة `databases:` كاملة، وغيّر
   `fromDatabase` إلى `sync: false`.
5. غيّر `storage_limit_bytes` من `1_073_741_824` إلى `524_288_000`
   (`app/config.py`) — سقف Supabase المجاني 500MB لا 1GB.

> **لماذا الخطوة ٥ بعد القطع لا قبله:** تغيير السقف قبل الانتقال يجعل تنبيه
> التخزين ينطلق كذباً بينما القاعدة ما زالت على Render بسقف 1GB.

### الخطوة ٨ — التقاعد (بعد أسبوع من التشغيل السليم، لا فوراً)

احتفظ بقاعدة Render أسبوعاً كاملاً بعد القطع. إن ظهر خلل، الرجوع خطوة واحدة
لا استعادة كاملة.

## ٤. ما يتغيّر في سلوك النظام بعد الانتقال

| البند | Render (الآن) | Supabase (بعد) |
|---|---|---|
| مدة الخطة المجانية | **تنتهي بعد ٣٠ يوماً** | دائمة |
| السقف | 1 GB | **500 MB** — نصف السعة |
| الخمول | لا إيقاف للقاعدة | **تتوقّف بعد ٧ أيام خمول** — الجامع الساعي يوقظها تلقائياً |
| زمن الشبكة | Oregon | سنغافورة — أقرب للخليج |

**السقف الأهم:** 500MB. بكثافة ٨٨٦ بايت للرابط (مقيسة في `docs/37`)، هذا
يعني ≈ **٦٠٠ ألف رابط** بدل ١٫٢ مليون. النصف.

---

## ٥. ما لم يُقَس ولا يُدّعى

- **زمن ذهاب-وإياب بين Render (Oregon) وSupabase (سنغافورة):** غير مقيس.
  المسافة كبيرة، والأثر على زمن الاستجابة حقيقي لكن مقداره غير معروف حتى
  يُقاس بعد القطع. لو تبيّن ثقيلاً، الخيار هو نقل خدمة الويب إلى منطقة
  أقرب لسنغافورة (بند M-06).
- **سلوك إيقاف Supabase بعد ٧ أيام:** موصوف من وثائق المزوّد لا من تجربة
  على هذا النشر.
