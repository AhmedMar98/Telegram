# عند انتهاء صلاحية قاعدة Render المجانية — البدائل

قاعدة Postgres المجانية على Render **محدودة المدة**. هذا ليس خطراً
محتملاً بل حدثاً مؤكّداً، والاستعداد له جزء من المشروع لا طارئ عليه.
(الفكرة ٧٠.)

القيد الحاكم كما هو: **صفر تكلفة، بلا Docker، بلا Oracle Cloud، وبلا أي
عملية خلفية دائمة.** أي بديل لا يستوفيها ليس بديلاً.

---

## ١. لماذا الانتقال سهل هنا

المشروع لا يستخدم أي امتداد Postgres خاص ولا ميزة مملوكة لمزوّد:

- البحث النصّي يستعمل `to_tsvector`/`plainto_tsquery` القياسيين، وهما في
  Postgres نفسه لا في امتداد.
- لا `pgvector` ولا `PostGIS` ولا `TimescaleDB`.
- المخطّط كله مملوك لـAlembic (`alembic/versions/`)، و`alembic upgrade
  head` يبنيه من الصفر على أي Postgres.
- الاتصال عبر متغيّر `DATABASE_URL` واحد، ولا شيء آخر يعرف أين القاعدة.

النتيجة: الانتقال = قاعدة جديدة + `alembic upgrade head` + استعادة نسخة +
تغيير `DATABASE_URL` في موضعين (Render وأسرار GitHub).

---

## ٢. البدائل، بشروطها المعلنة

> الأرقام أدناه هي ما تعلنه المزوّدات على صفحات تسعيرها. **تتغيّر.**
> تحقّق منها وقت الانتقال لا وقت قراءة هذا الملف — وهذا هو سبب عدم
> اختيار «الأفضل» هنا سلفاً.

| المزوّد | ما يميّزه | ما يجب الانتباه له |
|---|---|---|
| **Neon** | خطة مجانية دائمة لا محدودة المدة؛ Postgres حقيقي؛ تفريع القاعدة مفيد للتجارب | القاعدة **تنام** عند الخمول، فأول طلب بعدها يدفع تأخير إيقاظ — يضاف إلى تأخير إيقاظ Render نفسه |
| **Supabase** | Postgres حقيقي، ولوحة إدارة، ونسخ احتياطي مدمج | مشروع خامل قد يُوقَف؛ الحصّة المجانية تُقاس بالمشروع لا بالقاعدة |
| **Render (قاعدة جديدة)** | لا تغيير في أي شيء آخر | تنتهي صلاحيتها ثانيةً — يؤجّل المشكلة ولا يحلّها |

**التوصية العملية:** Neon هو الأقرب لروح القيد (مجاني **دائم** لا مؤقّت).
لكن التحقّق من الشروط وقت الانتقال شرط، لا مجاملة.

---

## ٣. إجراء الانتقال

1. **خذ نسخة من القاعدة الحالية قبل أي شيء.**
   ```bash
   pg_dump "$OLD_DATABASE_URL" --no-owner --no-privileges -Fc -f backup.dump
   ```
   `--no-owner --no-privileges` مهمّان: أدوار المزوّد القديم غير موجودة
   عند الجديد، وبدونهما تفشل الاستعادة على صلاحيات لا معنى لها.

2. **أنشئ القاعدة الجديدة** واحصل على رابط اتصالها.

3. **ابنِ المخطّط بالترحيلات لا بالاستعادة العمياء:**
   ```bash
   DATABASE_URL="postgresql+psycopg://..." python -m alembic upgrade head
   DATABASE_URL="postgresql+psycopg://..." python -m alembic check
   ```

4. **استعد البيانات فقط:**
   ```bash
   pg_restore --data-only --disable-triggers -d "$NEW_URL" backup.dump
   ```
   `--data-only` لأن المخطّط بُني في الخطوة ٣؛ خلط الاثنين يُنتج تعارضات
   على القيود والفهارس.

5. **حدّث `DATABASE_URL` في موضعين اثنين:**
   - لوحة Render (خدمة الويب)
   - أسرار GitHub Actions (المجمّع، وفاحص الحيوية، والكنس، والنسخ الاحتياطي)

   نسيان الثاني هو الخطأ المتوقّع: الموقع يعمل ويبدو كل شيء سليماً، بينما
   الجمع يكتب في قاعدة مهجورة. تحذير «لم يعمل الجمع التلقائي منذ…» في
   اللوحة هو ما يكشف ذلك.

6. **تحقّق:**
   ```bash
   curl -s https://<your-service>/readyz     # يعرض schema_version
   python scripts/db_report.py               # عدد الصفوف لكل جدول
   ```
   قارن الأعداد بما كان قبل الانتقال. `schema_version` يجب أن يطابق آخر
   ترحيل.

---

## ٤. ما يجب فحصه في أي بديل قبل الالتزام

- Postgres **حقيقي** (لا واجهة متوافقة جزئياً): `to_tsvector` و`GIN`
  والفهارس على التعبيرات كلها مستخدَمة فعلاً هنا.
- خطة مجانية **دائمة** لا تجريبية.
- اتصال خارجي مسموح (الجامع يعمل من GitHub Actions، خارج شبكة المزوّد).
- حدّ اتصالات كافٍ: خدمة الويب + ثلاث مهام مجدولة قد تتداخل.
- إمكانية `pg_dump` — بلا مخرج، البديل مصيدة لا حلّ.
