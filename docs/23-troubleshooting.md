# استكشاف الأخطاء — مشكلة ← سبب محتمل ← حلّ

الفكرة ٢٢٩. جدول لا سرد: من يفتح هذه الصفحة يفتحها وشيءٌ معطّل، فيقرأ
بالمسح لا بالتسلسل.

**كل صفّ هنا عطلٌ وقع فعلاً في هذا المشروع أو ينتج عن قيد موثَّق فيه.** ليس
قائمة أعطال عامّة منسوخة.

## النشر والإقلاع

| المشكلة | السبب المحتمل | الحلّ |
|---|---|---|
| البناء يفشل بـ`No module named 'psycopg2'` | Render يعطي `postgres://…` وSQLAlchemy يحلّه إلى psycopg2 غير المثبَّت | لا شيء — `normalize_database_url` في `app/config.py` يعالجها. إن ظهرت رغم ذلك فالمتغيّر لا يمرّ عبر `Settings` |
| الخدمة تُقلع ثم تموت فوراً | `alembic upgrade head` فشل قبل `uvicorn` | افتح سجلّ Render واقرأ خطأ الهجرة نفسه. الأمران متسلسلان في `startCommand` عمداً: قاعدة نصف مهاجَرة أسوأ من خدمة لا تُقلع |
| `/readyz` يردّ ٥٠٣ و`/healthz` يردّ ٢٠٠ | القاعدة غير متاحة، والخدمة نفسها حيّة | مقصود: `/healthz` لا يلمس القاعدة عمداً. راجع حالة قاعدة Render |
| أوّل طلب بعد فترة يتأخّر ~دقيقة | الخدمة نامت (خطة مجانية) | لا يُصلَح مجاناً — `docs/22-faq.md` |
| `new row violates row-level security policy for table "…"` | كتابة إلى جدول محمي بـRLS دون إعلان المستأجر | استدعِ `scope_session_to_workspace(db, workspace_id)` بعد أن يُعرَف المستأجر مباشرةً. `app/deps.py` يفعلها لطريق الطلب؛ السكربتات تفعلها صراحةً |
| `invalid input syntax for type integer: ""` من استعلام على جدول محمي | سياسة RLS بلا `NULLIF` — الإعداد المحلّي للمعاملة يعود إلى النصّ الفارغ لا NULL | راجع الترحيل `0020`؛ التعبير الصحيح `NULLIF(current_setting(…, true), '')::int`. يظهر ابتداءً من **الطلب الثاني** على الاتّصال لا الأوّل |
| كل الصفحات فارغة رغم وجود بيانات في القاعدة | المستأجر غير مضبوط: RLS يفشل مغلقاً فيرجع صفر صفوف | شغّل `rls_effective(db)` أوّلاً — يخبرك إن كانت الحماية فعّالة أصلاً — ثم تحقّق أن الطريق يمرّ بـ`app/deps.py` |
| مهمّة مجدولة تنجح وتُبلِّغ «لا شيء» بينما البيانات موجودة | السكربت يقرأ جدولاً محمياً ولم يستدعِ `scope_session_to_workspace` | هذا العطل **صامت** بالتصميم. `tests/test_rls_wiring.py` يمنع تكراره؛ إن ظهر فالسكربت جديد ولم يمرّ بالحارس |
| RLS مفعّل في `pg_class` لكنه لا يعزل شيئاً | إمّا الدور خارق (يتجاوز RLS دائماً) أو الجدول `ENABLE` بلا `FORCE` (المالك يتجاوزه) | `rls_effective(db)` يفرّق بين الحالتين ويسمّيها. لا تنشر بدور خارق |

## الحساب والدخول

| المشكلة | السبب المحتمل | الحلّ |
|---|---|---|
| التسجيل يردّ ٤٠٣ | `INVITE_CODE` مضبوط والرمز المُدخَل لا يطابقه | أدخل الرمز الصحيح، أو أفرغ المتغيّر لفتح التسجيل |
| التسجيل يردّ ٤٠٩ | البريد مستخدَم سلفاً | سجّل الدخول بدل التسجيل |
| الدخول يردّ ٤٢٩ | خانق محاولات الدخول | انتظر النافذة. الرقم في `app/security.py` |
| الدخول يطلب رمزاً ولا تملك التطبيق | التحقّق بخطوتين مفعَّل | استخدم أحد رموز الاسترداد العشرة |
| رمز TOTP صحيح ويُرفض | **الرمز نفسه استُخدم للتوّ** | انتظر الرمز التالي. إعادة استخدام رمز = إعادة تشغيل، وتُرفض عمداً |
| رمز TOTP يُرفض دائماً | ساعة الجهاز منحرفة | زامن ساعة الهاتف. النافذة ±٣٠ ثانية |

## الروابط والتصنيف

| المشكلة | السبب المحتمل | الحلّ |
|---|---|---|
| رابط أضفته لا يظهر في البحث | مؤرشف، والبحث يخفي المؤرشف افتراضياً | فعّل «إظهار المؤرشفة» |
| رسالة فيها ٦٠ رابطاً خزّنت ٥٠ | سقف `MAX_LINKS_PER_MESSAGE` | مقصود: ذيل الرسائل الطويلة قوائم مرايا غالباً. العدد المفقود مُحصى في تقرير التشغيلة |
| نفس الرابط مرّتين | جاء من قناتين | مقصود: مفتاح منع التكرار `(channel_id, url_hash)` — لكلّ صفّ سياقه. `docs/06-rejected.md` (الفكرة ٦٣) |
| التصنيف خاطئ باستمرار لنطاق واحد | قاعدة ناقصة | صحّحه من اللوحة. بعد ثلاث تصحيحات على النطاق نفسه يصلك تنبيه بذلك (الفكرة ١٦٣) |
| `classified_by` يقول `rules` دائماً | `GROQ_API_KEY` غير مضبوط، أو الحصّة نفدت | كلاهما سلوك مصمَّم لا عطل. راجع تنبيه `groq_quota` |

## الجمع من تلغرام

| المشكلة | السبب المحتمل | الحلّ |
|---|---|---|
| التشغيلة تنجح ولا تُجمَع روابط | لا قنوات نشطة، أو العلامة المائية عند آخر رسالة | طبيعي إن لم يُنشَر جديد |
| كل الحسابات تُخفق ويصلك تنبيه | جلسة ملغاة | أعد التفويض عبر `scripts/make_session_string.py` ثم `scripts/add_account.py` |
| `session string could not be decrypted` | `FIELD_ENCRYPTION_KEY` تغيّر بعد تخزين الصفّ | أعده إلى قيمته السابقة، أو دوّره بـ`scripts/rotate_encryption_key.py` مع `FIELD_ENCRYPTION_KEY_OLD` |
| الجامع يتوقّف في منتصف قناة | `FloodWaitError` من تلغرام | مُعالَج: ما جُمِع يُحفَظ والعلامة المائية تبقى متّصلة، وتُستأنف التشغيلة التالية |
| حساب تعطّل تلقائياً | إخفاقات متتالية بلغت الحدّ | `POST /channels/accounts/{id}/reactivate` بعد إصلاح السبب |

## البوت والتنبيهات

| المشكلة | السبب المحتمل | الحلّ |
|---|---|---|
| البوت لا يردّ إطلاقاً | `BOT_TOKEN` أو `PUBLIC_BASE_URL` غير مضبوط | كلاهما لازم: الـwebhook يُسجَّل عند الإقلاع من الثاني |
| البوت يردّ ولا تصل التنبيهات | المحادثة غير مربوطة بمساحة العمل | ولّد رمز ربط من اللوحة وأرسله للبوت |
| نوع تنبيه لا يصل أبداً | مطفأ — الملخّصات ومحتوى البالغين والتصنيف المتضارب **مطفأة افتراضاً** | فعّله من «مركز التنبيهات ← إعدادات التنبيهات» |
| لا تصل رسالة نسخ احتياطي أسبوعياً | التشغيلة لم تعمل أصلاً | هذا بالضبط ما يعنيه الغياب — `docs/19-runbook.md` §٥ |
| الـwebhook الخارجي يُرفض عند الحفظ | العنوان `http`، أو يشير إلى نطاق داخلي/محجوز | استخدم `https` ومضيفاً عامّاً. الرسالة تقول أيّ القاعدتين |
| الـwebhook مضبوط ولا يصل شيء | `last_status` في اللوحة يقول ما حدث | إن كان فارغاً فلم تُجرَّب بعد؛ اضغط «إرسال اختبار» |

## التطوير محلياً

| المشكلة | السبب المحتمل | الحلّ |
|---|---|---|
| `mypy` نظيف محلياً ويفشل في CI | `mypy` المحلي يحلّ `aiogram` إلى `Any` | `mypy --python-executable "$(which python3)" app scripts` |
| `ruff check --fix` يقول «لا إصلاحات» والبوّابة تفشل | تلك رسالة **خطأ** لا نجاح | البوّابة تنتهي بـ`ruff check .` مجرّداً |
| اختبارات بحث Postgres تفشل بلا سبب | `DATABASE_URL` و`PG_TEST_DSN` يشيران إلى القاعدة نفسها | `conftest.py` يرفض ذلك صراحةً. استخدم قاعدتين |
| اختبار وثيقة يقول «قديمة» | مُولَّدة والمصدر تغيّر | شغّل المولِّد المذكور في رسالة الفشل |
