# منصة استخبارات الروابط (Link Intelligence Platform)

جمع روابط من قنوات Telegram، تصنيفها تلقائياً، والبحث فيها — بتكلفة تشغيل **صفر** فعلياً، بدون Docker، منشورة على Render.

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/AhmedMar98/Telegram)

اضغط الزر أعلاه ← سجّل دخولك في Render ← وافق على وصول Render لهذا المستودع. سيقرأ `render.yaml` وينشئ **خدمة الويب + قاعدة البيانات** على الخطة المجانية تلقائياً، دون أي إعداد يدوي.

> المستودع خاص، لذا يجب أن تمنح Render صلاحية الوصول إليه عند أول ربط (زر "Configure account" في شاشة Render).

### ما الذي تتّسع له فعلاً — بأرقام مقيسة لا تقديرات

| السؤال | الجواب المقيس |
|---|---|
| كم رابطاً تتّسع له الخطة المجانية؟ | **~١٫٢ مليون** (حدّ ١ غيغابايت ÷ ٨٨٦ بايت للرابط، شاملةً الفهارس) |
| كم يستغرق البحث عند هذا السقف؟ | **٣٨–٢٠٢ ملّي ثانية** لمصطلح واقعي (< ١٪ من المجموعة) |
| كم تستغرق لوحة الإحصاءات؟ | **٧٫٩ ملّي ثانية** مخبَّأة، **١٫٠٩ ثانية** عند أوّل حساب |
| كم تستهلك من الذاكرة؟ | **٢٢٧ ميغابايت** من حدّ ٥١٢ |
| كم حجم صفحة النتائج على الشبكة؟ | **٢٬١٤٤ بايت** مضغوطة (٨٨٪ أقل من غير المضغوطة) |
| وماذا يحدث تحت طلبات متوازية؟ | **٤٠ تسجيل دخول متزامن في ٣٫٢ ثانية**، و`/healthz` يبقى تحت ٥٠٠ ملّي ثانية |

قِيست على PostgreSQL 16 حقيقي بـ**١٬٢٠٠٬٠٠٠ رابط = ١٫٠٠ غيغابايت بالضبط**،
عبر واجهة HTTP الحقيقية ومع تفعيل عزل الصفوف — التفصيل الكامل، بما فيه ما
**لا** تستطيع هذه الأرقام قوله، في [`docs/37-phase11-measurements.md`](docs/37-phase11-measurements.md).

## المعمارية (لماذا هي مجانية 100٪ فعلاً)

| المكوّن | أين يعمل | التكلفة |
|---|---|---|
| واجهة الويب + API + بوت Telegram (webhook) | خدمة ويب واحدة على Render (`free` plan) | 0 |
| قاعدة البيانات | Render Postgres (خطة `free`) | 0 — لكنّها **تُحذف بعد ٣٠ يوماً** (مؤكَّد من لوحة نشر حقيقي، لا من مصدر منشور). النسخ الاحتياطي الأسبوعي مفعّل، والاستعادة يدوية |
| جامع الروابط (Telethon) | GitHub Actions، مجدول (cron)، **ليس عملية دائمة** | 0 (لا توجد خطة عامل خلفي مجانية على Render إطلاقاً — لذلك لم نستخدم عملية دائمة) |
| النسخ الاحتياطي | GitHub Actions، أسبوعي، يُخزَّن كـ Artifact | 0 |
| التصنيف الأساسي | قواعد محلية (امتداد/نطاق/كلمات مفتاحية) — بدون أي استدعاء شبكي | 0 دائماً |
| التصنيف الإضافي (اختياري) | طبقة Groq API المجانية، تُستخدم فقط إذا ضُبط `GROQ_API_KEY` | 0، ولا تُعطّل شيئاً إن غابت |

لا يوجد أي Dockerfile في هذا المستودع — Render يشغّل الكود مباشرة عبر `runtime: python` في `render.yaml`.

## أربع طرق لإدخال الروابط (ثلاث لا تحتاج أي مفاتيح)

| الطريقة | تحتاج مفاتيح Telegram؟ | متى تستخدمها |
|---|---|---|
| **لصق يدوي** من لوحة التحكم | ❌ لا | الأسرع — الصق رابطاً أو رسالة أو قائمة، ويُصنَّف فوراً |
| **استيراد إشارات المتصفّح / Pocket / Instapaper** | ❌ لا | لنقل مجموعة قائمة عندك بالفعل |
| **استيراد أرشيف Telegram Desktop** | ❌ لا | لسحب تاريخ قناة كامل دفعة واحدة |
| **الجامع التلقائي** (كل ساعة) | ✅ نعم | للتشغيل المستمر بعد ضبط الأسرار |

النظام **يعمل بالكامل** بالطرق الثلاث الأولى. الجامع التلقائي تحسين لاحق، وليس شرطاً للتشغيل.

وللإدخال البرمجي هناك مسار خامس: `POST /links` بمفتاح API، ويقبل
`application/json` أو `text/plain` — فسطر واحد في الطرفية يكفي:

```bash
curl -X POST https://<your-app>/links \
  -H "Authorization: Bearer lipk_..." \
  -H "Content-Type: text/plain" \
  --data 'https://example.com/article'
```

### الطريقة ١: لصق يدوي
سجّل الدخول ← لوحة التحكم ← صندوق «إضافة روابط يدوياً» ← الصق أي نص ← «إضافة وتصنيف».

### الطريقة ٢أ: استيراد إشارات المتصفّح أو Pocket/Instapaper (بدون أي مفاتيح)

ملف تملكه أصلاً يكفي — لا `api_id` ولا session string ولا رمز دخول:

| المصدر | كيف تُصدّر |
|---|---|
| Chrome / Edge | الإشارات ← مدير الإشارات ← ⋮ ← تصدير الإشارات |
| Firefox | الإشارات ← إدارة الإشارات ← استيراد ونسخ احتياطي ← تصدير إلى HTML |
| Safari | ملف ← تصدير ← الإشارات |
| Pocket | getpocket.com/export |
| Instapaper | الإعدادات ← تصدير ← تنزيل ملف CSV |

```bash
python scripts/import_bookmarks.py bookmarks.html --workspace 1
python scripts/import_bookmarks.py chrome.html pocket.csv --workspace 1   # عدّة ملفات دفعة واحدة
```

**الصيغة تُكتشف من محتوى الملف لا من امتداده**، فملف Pocket محفوظ بامتداد
`.txt` يعمل. و`--dry-run` يعرض ما سيُستورَد بلا كتابة.

**ما لا يُستورَد أبداً:** كل ما ليس `http`/`https` — أي bookmarklets
(`javascript:`) وصفحات المتصفّح الداخلية (`chrome://`، `place:`) وملفات
محلية (`file:`). تُعدّ وتُبلَّغ صراحةً كي لا يبدو النقص عطلاً. كل ملف يصير
قناة مستقلّة باسمه: إشارات المتصفّح ومحفوظات Pocket مجموعتان مختلفتان،
ودمجهما يمحو المعلومة الوحيدة عن مصدر كل رابط.

### الطريقة ٢ب: استيراد أرشيف Telegram Desktop (بدون أي مفاتيح)

1. في Telegram Desktop: افتح القناة ← قائمة **⋯** ← **Export chat history**.
2. أزل علامة الوسائط (نحتاج النص فقط، فيصبح التصدير سريعاً وصغيراً)، واختر **Format: JSON** ← Export.
3. ستحصل على `result.json`، ثم:

```bash
python scripts/import_telegram_export.py result.json --workspace 1
# أضف --dry-run لمعاينة ما سيُستورد دون كتابة أي شيء
```

يستخرج المستورِد حتى الروابط المخفية خلف نص («اضغط [هنا]») التي لا تظهر في نص الرسالة.

### تجربة سريعة ببيانات واقعية

```bash
python scripts/seed_demo.py
```

ينشئ حساباً تجريبياً و١٦ رابطاً موزعة على ٤ قنوات، فترى التصنيف والبحث يعملان فوراً.

## خطوات النشر الفعلي

### ١. نشر الخدمة وقاعدة البيانات

1. اضغط زر **Deploy to Render** في أعلى هذا الملف (أو افتح <https://dashboard.render.com/blueprints> ← "New Blueprint Instance" واختر المستودع يدوياً). Render يقرأ `render.yaml` وينشئ خدمة الويب + قاعدة البيانات على الخطة المجانية تلقائياً.

   ما يُضبط تلقائياً دون تدخل منك: `DATABASE_URL` (يُربط بقاعدة البيانات مباشرة)، و`SECRET_KEY` و`BOT_WEBHOOK_SECRET` (يولّدهما Render عشوائياً)، و`PYTHON_VERSION` و`ENVIRONMENT`.

2. بعد أول نشر ناجح، اضبط القيم الاختيارية من لوحة Render (Environment):
   - `INVITE_CODE` — رمز دعوة يمنع أي زائر عشوائي من إنشاء حساب على الرابط العام (اختياري لكن مستحسن لأداة داخلية).
   - `PUBLIC_BASE_URL` — الرابط الذي يعطيك إياه Render بعد أول نشر، مثل `https://link-intel-web.onrender.com`.
   - `BOT_TOKEN` — بعد إنشاء بوت عبر [@BotFather](https://t.me/BotFather) (اختياري، فقط إن أردت تفعيل بوت Telegram).
3. أعد نشر الخدمة بعد ضبط `PUBLIC_BASE_URL` حتى يُسجَّل webhook البوت تلقائياً عند الإقلاع.

### ١أ. البوت مقابل حساب الجمع — بوت واحد، وحساب أو أكثر

خلطُ الاثنين هو أكثر سوء فهم شائع في الإعداد، فالتفريق صريح هنا:

| | ما هو | العدد | لماذا |
|---|---|---|---|
| **البوت** | حساب Bot API من [@BotFather](https://t.me/BotFather) | **واحد** | واجهة بحث واستعلام من داخل تيليجرام |
| **حساب الجمع** | حسابك الشخصي عبر Telethon (session string) | **واحد أو أكثر** | يقرأ القنوات ويجمع الروابط |

**لماذا لا يكفي البوت للجمع؟** Bot API لا يسمح للبوت بقراءة رسائل قناة ليس
مشرفاً فيها. القنوات التي تُجمَع منها ليست ملكك، فلا سبيل لجعل البوت مشرفاً
عليها. الجمع يتمّ بحساب مستخدم عادي — وهو ليس بوتاً.

**ولماذا بوت واحد لا عدّة؟** البوت هنا واجهة استعلام لا عامل. كل مساحة عمل
تربط محادثتها بالبوت نفسه عبر رمز ربط، والعزل يقع في قاعدة البيانات على
`workspace_id` لا بتعدّد البوتات. بوت ثانٍ = توكن ثانٍ وويب-هوك ثانٍ بلا مكسب.

تعدّد **حسابات الجمع** مدعوم (`scripts/add_account.py`)، وكل قناة تُسنَد إلى
حساب — يفيد عند كثرة القنوات لتوزيع حدود تيليجرام.

### ١ب. ربط البوت

1. [@BotFather](https://t.me/BotFather) ← `/newbot` ← احتفظ بالتوكن.

   > ⚠️ **التوكن مفتاح تحكّم كامل بالبوت.** من يملكه يقرأ رسائله ويرسل باسمه.
   > لا تضعه في لقطة شاشة ولا في محادثة ولا في المستودع — مكانه الوحيد
   > متغيّر `BOT_TOKEN` في لوحة Render. إن تسرّب: BotFather ← `/revoke`.

2. في Render اضبط: `BOT_TOKEN`، و`BOT_WEBHOOK_SECRET` (نصّ عشوائي من عندك، لا
   من BotFather)، و`PUBLIC_BASE_URL`.
3. **لا تسجّل الـwebhook يدوياً**: الخدمة تفعلها عند الإقلاع
   (`app/main.py`)، على المسار `PUBLIC_BASE_URL/telegram/webhook/BOT_WEBHOOK_SECRET`.
   السرّ جزء من المسار، فأي طلب لا يعرفه يُقابَل بـ404 ولا يستطيع أحد حقن
   تحديثات مزيّفة.
4. من لوحة التحكم ← قسم «البوت» ← «توليد رمز ربط» ← أرسل للبوت `/start <الرمز>`.
   الرمز صالح **مرّة واحدة**.

> على الخطة المجانية: أول رسالة بعد ١٥ دقيقة خمول قد تتأخّر نحو دقيقة ريثما
> تستيقظ الخدمة. مقايضة مقصودة مقابل عدم وجود عملية دائمة.

### ١ج. إدارة حسابات الجمع

| الإجراء | كيف |
|---|---|
| إضافة حساب | `TG_SESSION_STRING="..." python scripts/add_account.py --workspace-id 1 --label "الهاتف الثاني"` |
| **إزالة حساب** | `python scripts/remove_account.py --workspace-id 1 --label "..."` — يعيد قنوات الحساب إلى الحساب الافتراضي **ثم** يحذفه |
| معرفة الحالة | قسم «حسابات الجمع» في اللوحة، أو `GET /channels/accounts` |
| إعادة تفعيل حساب عُطِّل تلقائياً | زر في اللوحة، أو `POST /channels/accounts/{id}/reactivate` — **بعد إصلاح السبب**، فلا شيء هنا يستطيع التحقّق من ذلك |
| الحدّ الأقصى للحسابات | `MAX_ACCOUNTS_PER_WORKSPACE` (الافتراضي ٥) |
| توزيع القنوات | `COLLECTOR_MAX_CHANNELS_PER_ACCOUNT` (الافتراضي ٢٠) |

> **حذف حساب ما يزال يملك قنوات كان يفشل تماماً** بخطأ مفتاح أجنبي — تحقّقنا من ذلك عملياً. لذلك `remove_account.py` يعيد القنوات إلى الحساب الافتراضي أولاً (`account_id = NULL`، وهو ما يعنيه NULL في كل مكان آخر)، فتستمرّ القنوات في الجمع بدل أن تصمت. ويرفض السكربت إزالة **آخر** حساب في مساحة العمل: ذلك يوقف الجمع كلياً، وهو قرار لا يتّخذه أحد بتشغيل أمر تنظيف.

> **الحساب الذي يفشل ٣ مرات متتالية يُعطَّل تلقائياً** مع تسجيل السبب. قبل ذلك كانت جلسة ملغاة تُعاد محاولتها كل ساعة إلى الأبد، وتُسجَّل رسالة خطأ لا يقرؤها أحد، بينما قنواتها لا تجمع شيئاً. واللوحة تفرّق بين تعطيل تلقائي (يحتاج فحصاً) وتعطيل يدوي (كان مقصوداً).

**أوامر البوت بعد الربط:** `/search` (يدعم `-كلمة` للاستبعاد)، `/latest`،
`/favorite`، `/details N`، `/stats`، `/vitality`، `/channels`، `/unlink`،
`/help`. ويمكن كذلك لصق رابط مباشرة لحفظه، أو كتابة كلمة مجرّدة للبحث بها.

### ٢. إنشاء مساحة العمل الأولى

افتح رابط الموقع → "تسجيل" → أنشئ الحساب (وهو تلقائياً يصبح مساحة عمل جديدة معزولة بالكامل). من صفحة `/auth/me` أو من أدوات المتصفح احصل على `workspace_id` — ستحتاجه في الخطوة التالية.

### ٣. تفعيل الجامع التلقائي (اختياري)

> النظام يعمل بدون هذه الخطوة عبر اللصق اليدوي أو استيراد الأرشيف (انظر أعلاه). أكملها فقط إن أردت تجميعاً تلقائياً مستمراً.

الجامع لا يعمل كعملية دائمة (Render لا يوفر ذلك مجاناً)، بل كمهمة مجدولة في GitHub Actions تعمل مرة كل ساعة.

1. شغّل محلياً (على جهازك، وليس في أي CI):
   ```bash
   pip install -r requirements-collector.txt
   python scripts/make_session_string.py
   ```
   أدخل رقم هاتفك وكود الدخول الذي يرسله Telegram (ويدعم السكربت التحقق بخطوتين إن كان مفعّلاً).

   > ⚠️ الناتج "session string" **يعادل كلمة مرور حسابك على تيليجرام** — من يملكه ينتحل شخصيتك. شغّل هذا السكربت على جهازك أنت فقط، والصقه مباشرة في أسرار GitHub، ولا تحفظه في ملف ولا ترسله في أي محادثة (بما في ذلك لي).
2. من إعدادات المستودع على GitHub (Settings → Secrets and variables → Actions) أضف:
   - `TG_API_ID`, `TG_API_HASH` — من <https://my.telegram.org>
   - `TG_SESSION_STRING` — الناتج من الخطوة السابقة
   - `DATABASE_URL` — نفس رابط قاعدة بيانات Render (Internal/External connection string من لوحة Render)
   - `COLLECTOR_WORKSPACE_ID` — الرقم الذي حصلت عليه في الخطوة ٢
   - `FIELD_ENCRYPTION_KEY` — يشفّر session string قبل تخزينه في القاعدة (بلا هذا السرّ، تسريب نسخة من القاعدة يعادل تسريب الحساب نفسه). ولّده بـ:
     ```bash
     python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
     ```
   - `GROQ_API_KEY` (اختياري) — لتفعيل طبقة التصنيف الإضافية المجانية من <https://console.groq.com>
3. من تبويب Actions شغّل workflow "Collector" يدوياً أول مرة (`workflow_dispatch`) للتأكد أنه يعمل، ثم سيعمل تلقائياً كل ساعة.
4. أضف القنوات المراد جمعها من لوحة التحكم في الموقع (`/dashboard` → "القنوات") — الحساب المستخدم في التوكن يجب أن يكون عضواً في تلك القنوات.

#### تعدّد حسابات الجمع (اختياري)

حساب واحد يكفي تماماً. إن أردت توزيع القنوات على أكثر من حساب — لتخفيف ضغط الطلبات على أي حساب منفرد — سجّل حساباً إضافياً:

```bash
TG_SESSION_STRING="<session string الحساب الجديد>" \
  python scripts/add_account.py --workspace 1 --label "second"
```

> السرّ يُقرأ من متغيّر البيئة لا من وسيط سطر الأوامر عمداً: الوسائط تظهر لأي عملية أخرى على الجهاز في قائمة العمليات وتُحفظ في تاريخ الصدفة. يُشفَّر قبل تخزينه تماماً كالحساب الأساسي.

ثم من لوحة التحكم (قسم «القنوات») اختر الحساب المسؤول عن كل قناة من القائمة المنسدلة. القنوات غير المعيَّنة يجمعها الحساب الافتراضي (الأقدم)، فلا شيء يتوقف إن لم تعيّن شيئاً.

**عزل الأعطال**: إن فشل حساب (جلسة ملغاة، حظر، انقطاع شبكة) يسجَّل الخطأ ويكمل الجامع بقية الحسابات — لا تضيع قنوات الحسابات السليمة بسبب حساب واحد معطوب.

> تعدّد الحسابات يوزّع الحمل، ولا يضمن تفادي الحظر: خوارزميات تيليجرام غير معلنة.

#### تدوير مفتاح التشفير (عند الحاجة)

إن تسرّب `FIELD_ENCRYPTION_KEY` أو أردت تدويره دورياً:

```bash
# ١) ولّد مفتاحاً جديداً
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

# ٢) عاين ما سيتغيّر — لا يكتب شيئاً
FIELD_ENCRYPTION_KEY_OLD="<المفتاح الحالي>" FIELD_ENCRYPTION_KEY="<الجديد>" \
  python scripts/rotate_encryption_key.py --dry-run

# ٣) نفّذ فعلياً
FIELD_ENCRYPTION_KEY_OLD="<المفتاح الحالي>" FIELD_ENCRYPTION_KEY="<الجديد>" \
  python scripts/rotate_encryption_key.py

# ٤) حدّث FIELD_ENCRYPTION_KEY في أسرار GitHub ولوحة Render
```

السكربت **مقاوم للتكرار**: تشغيلة متوقّفة في منتصفها تُستأنف بإعادة تشغيلها بلا ضرر. وإن وجد صفاً لا يُفكّ بأيٍّ من المفتاحين، **يتوقّف قبل الكتابة** بدل ترك الجدول موزّعاً على مفتاحين.

### ٤. تأكد أن كل شيء موصول (خطوة واحدة)

بعد إضافة الأسرار، لا تنتظر الجامع ليفشل بصمت — افحص الإعداد مباشرة:

**من GitHub** (الأسهل): تبويب Actions ← "Verify setup" ← Run workflow. سيقرأ أسرارك ويخبرك بالضبط ما الناقص.
**أو محلياً**: `python scripts/check_setup.py`

> **البوت لا يردّ؟** لا تخمّن. `check_setup.py` يفحص الإعدادات فقط؛ السؤال
> الحقيقي هو **هل قبل تيليجرام ويبهوكاً، وماذا حدث في آخر تسليم؟** — وجوابه
> في زرّ **«لماذا لا يردّ البوت؟»** بلوحة التحكم، أو `python scripts/check_bot.py`
> حيث توجد طرفية. الزرّ موجود لأنّ **الخطة المجانية في Render بلا Shell**،
> فالسكربت غير قابل للتشغيل على النشر الذي يستهدفه هذا المشروع أصلاً.
> يميّز أربع حالات تبدو متطابقة من الخارج: رمز مُبطَل، ولا ويبهوك، وويبهوك
> على عنوان قديم، وويبهوك سليم يفشل تسليمه — والأخيرة يجيب عنها
> `last_error_message` من تيليجرام، وهي غير مرئية من طرفك إطلاقاً.

الأداة لا تطبع أي قيمة سرية إطلاقاً — تخبرك فقط بحالة كل عنصر:

```
[ OK ] database: reachable (postgresql)
[ OK ] schema: 6 core tables present
[ OK ] workspace: id 1 ("مساحتي")، 1 user(s)
[WARN] channels: no active channels — add them in the dashboard, or nothing is collected
[FAIL] telegram: partially configured, missing: TG_SESSION_STRING
[WARN] llm tier: GROQ_API_KEY set but rejected by Groq — paste a fresh key from console.groq.com
```

`FAIL` = يجب إصلاحه، `WARN` = ميزة اختيارية معطّلة والنظام يعمل بدونها.

**مفتاح Groq يُختبَر فعلاً لا يُفترَض:** مفتاح ملغى موجود في البيئة وميّت تماماً،
و«موجود» كانت ستخفي بالضبط العطل الذي يوجد هذا الفحص لكشفه. الاختبار عبر
`GET /models` فلا يستهلك أي حصّة، ونتيجته **لا ترفع رمز الخروج أبداً** — الطبقة
اختيارية بالتصميم، فمفتاح ميّت يقلّل الدقّة ولا يكسر النظام.

### ٥. النسخ الاحتياطي الأسبوعي

workflow باسم "Weekly DB backup" يعمل تلقائياً كل أسبوع وينتج نسخة `pg_dump` كـ Artifact على GitHub (يبقى محفوظاً ٣٥ يوماً). هذا تعويض عن كون قاعدة بيانات Render المجانية محدودة المدة — عند إعادة الإنشاء، نزّل آخر artifact واستورده:

```bash
pg_restore --no-owner --clean --if-exists -d "$NEW_DATABASE_URL" backup.dump
```

### ٦. التحقق التلقائي من حيوية الروابط

workflow باسم "Link vitality check" يعمل تلقائياً كل ٦ ساعات (`workflow_dispatch` متاح أيضاً للتشغيل الفوري). لا يحتاج أي سرّ إضافي غير `DATABASE_URL` نفسه — لا علاقة له بحسابات تيليجرام.

كل تشغيلة تفحص دفعة محدودة من الروابط (التي لم تُفحص قط أولاً، ثم الأقدم فحصاً) بطلب HTTP واحد لكل رابط، وتُسجّل `is_alive`/`http_status`/`last_checked_at`. هذا فحص وصول (reachability) لا فحص محتوى — صفحة "تم الحذف" تُعرَض عبر جافاسكربت من جهة العميل ستظهر "حيّة" (200) رغم أن المحتوى فعلياً غائب؛ والعكس صحيح أحياناً (حجب مؤقت لعنوان User-Agent غير مألوف قد يُسجَّل خطأً كرابط ميت). اعتبر `is_alive=false` "يستحق نظرة ثانية"، لا حقيقة نهائية تُستخدَم للحذف التلقائي.

## الأمان المطبَّق فعلياً

| الإجراء | التفاصيل |
|---|---|
| كلمات المرور | تُخزَّن مُجزَّأة بـ bcrypt فقط (معامل الكلفة قابل للضبط عبر `BCRYPT_ROUNDS`) |
| الجلسات | رمز عشوائي ٢٥٦-بت؛ القاعدة تخزّن SHA-256 له فقط، فتسريب قاعدة البيانات لا يُمكّن من انتحال جلسة |
| إلغاء الجلسة | فوري عند تسجيل الخروج (تحقق من القاعدة في كل طلب، لا انتظار انتهاء صلاحية الكوكي) |
| تقييد المحاولات | ٨ محاولات فاشلة خلال ١٥ دقيقة لكل بريد ⟵ حجب مؤقت (٤٢٩)، ولا يتأثر أي حساب آخر |
| منع استكشاف الحسابات | البريد غير الموجود يستهلك نفس زمن التحقق الحقيقي، والرد مطابق تماماً لحالة كلمة المرور الخاطئة |
| رمز الدعوة | مقارنة ثابتة الزمن (`secrets.compare_digest`) |
| عزل مساحات العمل — الطبقة الأولى | كل صف يحمل `workspace_id`، وكل استعلام مفلتَر به — مغطّى باختبار يفحص **كل** نقطة نهاية تأخذ مُعرِّف مورد |
| عزل مساحات العمل — الطبقة الثانية (RLS) | **سبعة جداول تحت سياسة عزل في PostgreSQL نفسه** (`ENABLE` + **`FORCE`**). تحمي ما لا يحميه الترشيح: **الكتابة** عبر المستأجرين. أيّ طريق يصل إلى القاعدة — سكربت مجدول، مهمّة صيانة، استعلام مكتوب على عجل — يخضع لها. تفشل **مغلقة**: سياق غير مضبوط يقرأ صفراً ولا يكتب شيئاً |
| متى لا يحمي RLS شيئاً | إن كان مستخدم القاعدة **خارقاً** (superuser) فهو يتجاوز RLS دائماً، حتى مع `FORCE`. `python scripts/check_setup.py` يقول لك أيّ الحالتين أنت فيها بدل أن تفترض |
| جداول خارج RLS عمداً | `links` و`telegram_accounts` (سكربتان يمسحانهما عبر كل المساحات)، و`users`/`api_keys`/`bot_links`/`bot_link_codes` (تُقرَأ **ليُعرَف** المستأجر — لا يمكن حراستها بآلية تشترط معرفته). مذكورة في `app/rls.py` بأسبابها لا مسكوتاً عنها |
| سجل التدقيق | كل عملية حساسة (تسجيل، دخول، خروج، إضافة/تعطيل قناة، تشغيل الجامع) تُكتب في `audit_log` |
| سياسة كلمة المرور | ٨ أحرف على الأقل، بلا قواعد تركيب إجبارية وبلا انتهاء دوري (مراجعة NIST SP 800-63B)، مع رفض كلمات المرور الأكثر شيوعاً في التسريبات |
| أصل الجلسة | كل جلسة تسجّل عنوان IP والمتصفح، فتعرف أي جهاز تُنهي — إرشادي لا موثوق (يأتي من ترويسة يرسلها العميل) |
| رؤية الهجمات | قسم «نشاط الأمان» في اللوحة يعرض محاولات الدخول الفاشلة وعدد العناوين المختلفة — الحجب وحده لا يخبرك أن أحداً يحاول |
| حد حجم الطلب | ١ ميغابايت، مرفوض قبل أي تحليل — لا يُحمَّل جسم ضخم في الذاكرة ثم يُرفض |
| تدوير مفتاح التشفير | `scripts/rotate_encryption_key.py` (معاينة جافّة، مقاوم للتكرار، يرفض العمل عند صف غير قابل للفك) |

## إدارة الروابط

| الإجراء | كيف |
|---|---|
| تصحيح تصنيف خاطئ | من لوحة التحكم، غيّر القائمة المنسدلة بجانب الرابط. التصحيح اليدوي يُسجَّل كـ`manual` بثقة ١٠٠٪ ولا تُعيد أي طبقة تلقائية الكتابة فوقه |
| حذف رابط | زر «حذف» بجانب الرابط. الحذف تنظيف وليس حظراً — إن أعيد جمع الرسالة نفسها سيعود الرابط |
| تصدير كل شيء | زر «تصدير CSV» (أو `GET /links/export.csv`). يحترم فلتر التصنيف الحالي |
| تصفح النتائج | أزرار «السابق/التالي» أسفل النتائج |
| فلترة حسب الحيوية | `GET /links?alive=true` أو `?alive=false` — الروابط التي لم تُفحص بعد لا تُدرَج في أيّ منهما |
| فهم سبب «الميتة» | الشارة بجانب الرابط تفرّق بين «غير موجودة» (٤٠٤) و«محجوبة عن الفاحص» (٤٠٣) و«الخادم يحدّ الطلبات» (٤٢٩) و«عطل مؤقّت» (5xx). مرّر المؤشّر لترى آخر مرة كان فيها الرابط حيّاً وعدد الإخفاقات المتتالية |
| أرشفة رابط ميت | زر 🗄 بجانب الرابط: يخرجه من نتائج البحث الافتراضية دون حذفه. «إظهار المؤرشفة» يعيده، والتصدير يشمله دائماً |
| فرز حسب الأحدث فحصاً | `?sort=checked` — سؤال مختلف عن «الأحدث جمعاً»: ما الذي أعرف الآن أنه يعمل |
| استبعاد كلمة من البحث | اكتب `-كلمة` ضمن البحث: `دورة بايثون -مدفوعة`. الشرطة داخل كلمة (`python-book`) ليست استبعاداً |
| فلترة حسب النطاق | زر «مشابهة» بجانب أي رابط، أو `GET /links?domain=example.com`. يُلغى من الإشعار تحت شريط البحث |
| فرز حسب أكثر النطاقات تكراراً | `?sort=domain_frequency` |
| حفظ بحث متكرّر | زر «احفظ البحث الحالي» — يُخزَّن على الخادم لا في المتصفّح، فيظهر على كل أجهزتك |
| مشاركة توليفة فلاتر | زر «انسخ رابط الفلاتر»: الفلاتر تُكتب في شريط العنوان دائماً، وفتح الرابط يعيد ضبطها |
| تصدير نتائج البحث | الأزرار الثلاثة (CSV / JSON / Markdown) تحترم كلمة البحث والتصنيف معاً. Markdown مجمّع حسب التصنيف وقابل للّصق في رسالة |
| عرض شبكي | زر «عرض شبكي»؛ الاختيار محفوظ في المتصفّح |
| إعادة اكتشاف القديم | زر «اكتشاف عشوائي»: خمسة روابط عشوائية من مساحة عملك |
| اختصارات | `/` ينقلك إلى حقل البحث، `Esc` يلغي حذفاً معلّقاً أو يفرغ البحث. لا اختصارات أخرى — الحقول تبقى قابلة للكتابة |
| التراجع عن حذف | الحذف لا يُرسَل إلى الخادم إلا بعد ٥ ثوانٍ؛ زر «تراجع» خلالها يلغيه فعلياً |
| كثافة العرض | زر واحد يدور بين: قائمة (مع نصّ الرسالة) ← شبكي ← مضغوط (سطر لكل رابط) |
| معرفة أن الجمع توقّف | تحذير أعلى النتائج إن مرّ أكثر من ٢٤ ساعة دون تشغيلة جمع. مساحة عمل يدوية بحتة لا تُحذَّر |

## الإتاحة

الواجهة مُتحقَّق منها في متصفّح حقيقي، لا بالترميز وحده:

| البند | الحالة |
|---|---|
| تباين WCAG 2.1 AA | كل أزواج النصّ/الخلفية مقيسة بالصيغة الرسمية في الوضعين. حدود الحقول كانت تسقط (١٫٥٤ و١٫٥٦ مقابل حدّ ٣٫٠) وصُحّحت |
| قارئ الشاشة | كل حقل له `<label>`، وكل زر أيقوني (★ ⧉ 🗄) له `aria-label`، والحالات تُعلَن عبر `aria-live` |
| لوحة المفاتيح | كل شيء قابل للوصول بـTab بترتيب مطابق للترتيب البصري، وحلقة التركيز ظاهرة في الوضعين |
| التكبير | ١٥٠٪ و٢٠٠٪ دون كسر التخطيط |
| RTL | الروابط اللاتينية معزولة بـ`unicode-bidi` فلا تتبعثر داخل النصّ العربي |
| الحركة | `prefers-reduced-motion` مُحترَم |
| اللمس | حدّ أدنى ٢٫٢٥rem لكل زر (WCAG 2.5.8) |
| فلترة حسب القناة | قائمة «كل القنوات» في صف البحث، أو `GET /links?channel_id=N`. تعمل مع البحث والتصنيف معاً |
| فلترة حسب اللغة | قائمة «كل اللغات» (عربي / إنجليزي / مختلط)، أو `GET /links?language=ar`. الكشف مبني على الكتابة لا على لغة معلنة، والروابط تُستبعد من العدّ قبله |
| معرفة سبب التصنيف | مرّر المؤشّر فوق نسبة الثقة بجانب الرابط: يظهر اسم القاعدة التي أطلقته (مثل `extension:pdf`) |
| معرفة مصدر الرابط | شارة بجانب الرابط تقول «من زر» أو «من رابط مخفي» أو «محوَّل عن: …». الروابط من نصّ الرسالة مباشرة لا تحمل شارة |
| ملاحظة على رابط | `PATCH /links/{id}/notes` — ملاحظتك الخاصة، منفصلة عن نصّ الرسالة الأصلي فلا يمحو أحدهما الآخر |
| تثبيت مرجع دائم | `POST /links/{id}/pin` — منفصل عن المفضّلة عمداً: «أحبّه» شيء و«أرجع إليه دائماً» شيء آخر |
| عدّ فتحات الرابط | افتح عبر `/links/{id}/open` — يعدّ ثم يحوّل. **العدّ ناقص عمداً**: من ينسخ الرابط بدل الضغط لا يظهر هنا |
| مراقبة حجم القاعدة | `python scripts/db_report.py`، ولوحة التحكم تعرض `storage`. الحجم يظهر على Postgres فقط؛ على SQLite تُعاد `None` بدل رقم مُختلَق |
| مخطط قاعدة البيانات | `docs/12-schema.md` — مولَّد من النماذج بـ`python scripts/db_report.py --schema`، واختبار يفشل إن صار قديماً |
| سياسة الاستبقاء | `docs/13-retention.md` — ما يبقى وكم ولماذا، والكنس المجدول في `.github/workflows/prune.yml` |
| سجل تصحيحات التصنيف | `GET /links/feedback` — كل تصحيح بشري مع ما قاله المصنّف وثقته وقاعدته. `?link_id=N` يعطي تاريخ رابط واحد |

> التصحيح البشري يُحفَظ حتى بعد حذف الرابط: أنفع تصحيح للتعلّم منه هو غالباً على رابط حُذف لاحقاً. يُمحى مع حذف مساحة العمل، لا قبله.


> التصدير ليس رفاهية: قاعدة البيانات المجانية محدودة المدة، فالقدرة على إخراج بياناتك دون الوصول لقاعدة البيانات جزء من المنتج.

> **الفاحص لا يقتل رابطاً بردّ واحد.** رمز ٤٢٩ (الخادم يحدّ الطلبات) أو 5xx يعني أن الخادم لم يستطع الإجابة الآن، لا أن الرابط اختفى — فتبقى حالة الرابط كما هي حتى تتكرّر ثلاث مرات متتالية. أما ٤٠٤ فلا لبس فيها ويُسجَّل الرابط ميتاً فوراً. والرابط الذي أخفق ثلاث مرات يُعاد فحصه كل ٣ أيام بدل كل ٦ ساعات، توفيراً لحصّة الفحص للروابط الجديدة. المفضّلة تُفحص أولاً.

## إدارة الحساب

| الإجراء | كيف |
|---|---|
| تغيير كلمة المرور | قسم «الحساب» في لوحة التحكم؛ يُبطل تلقائياً كل الجلسات الأخرى (لا هذه الجلسة) |
| تسجيل الخروج من كل الأجهزة | زر واحد يُبطل كل الجلسات النشطة فوراً بما فيها الحالية |
| إعادة تسمية مساحة العمل | قسم «مساحة العمل» أو `PATCH /auth/workspace`. مساحة العمل تُستنتج من الجلسة لا من المسار، فلا يوجد معرّف يمكن استبداله لإعادة تسمية مساحة غيرك |
| تبديل المظهر | زر في أعلى الصفحة يدور بين **تلقائي** (يتبع نظام التشغيل) و**فاتح** و**داكن**. الاختيار يُحفظ في المتصفح ويُطبَّق قبل أول رسم فلا وميض |
| تنزيل كل بياناتي | قسم «بياناتي» أو `GET /auth/me/export` — ملف JSON واحد يضم مساحة العمل والمستخدمين والقنوات والروابط وسجل التدقيق. لا يحتوي أي كلمة مرور ولا أي session string |
| حذف مساحة العمل نهائياً | `POST /auth/me/delete` — يتطلّب كلمة المرور **و** كتابة `DELETE` حرفياً. يمحو كل شيء ولا يمكن التراجع |
| **التحقّق بخطوتين (اختياري)** | قسم «التحقّق بخطوتين» أو `POST /auth/totp/setup` ثم `/enable`. TOTP قياسي يعمل مع أي تطبيق مُصادِق، **بلا أي خدمة خارجية** (`pyotp` محلياً). التفعيل **يُصدر ١٠ رموز استرداد تُعرض مرّة واحدة** — وهي ليست إضافة بل شرط: مستخدم واحد لكل مساحة عمل وبلا مسؤول، ففقدان الهاتف بلا رموز = فقدان دائم للمجموعة. السرّ **مشفَّر** في القاعدة والرموز **مجزّأة**، والرمز المستعمَل **لا يُقبل مرّتين** داخل نافذته |
| تنزيل سجل الأمان | قسم «سجل الأمان» أو `GET /auth/me/security-export` — الجلسات ومحاولات الدخول وحالة التحقّق بخطوتين والأحداث الحسّاسة فقط، **بلا أي روابط أو محتوى مجموع**. أضيق من التصدير الكامل عمداً، فيمكن مشاركته مع من يساعدك في التحقيق |
| تنبيه دخول من جهاز جديد | يصل عبر **البوت** إن كان مربوطاً — القناة المجانية الوحيدة (البريد يحتاج مزوّد SMTP وبياناته). **لا يعطّل الدخول أبداً**: فشل التنبيه ليس فشل مصادقة |
| مفاتيح API | قسم «مفاتيح API» أو `POST /auth/api-keys`. للاستخدام البرمجي عبر `Authorization: Bearer lipk_…` بدل الكوكي. **المفتاح ليس تسجيل دخول**: يقرأ الروابط ويضيفها ويصدّرها، و**لا يستطيع** حذف مساحة العمل، ولا تغيير كلمة المرور، ولا إنهاء الجلسات، ولا سرد أجهزتك، ولا إنشاء مفتاح آخر — وإلّا لصار إبطال المفتاح مسرحية. يُعرض مرّة واحدة عند الإنشاء ولا يُخزَّن إلا مجزّأً |
| نظرة سريعة على الحساب | `GET /auth/me/summary` — الهوية والأعداد وصحّة حسابات الجمع والجلسات في نداء واحد. **تجميع لا مصدر حقيقة ثانٍ**: كل رقم فيه تنتجه الدالة نفسها التي تخدمه منفرداً، واختبار يقارن كل حقل بالنقطة التي تملكه |

## الجلسات والأجهزة

- رتّب النتائج حسب الأحدث، النطاق، التصنيف، أو نسبة الثقة.
- إحصاءات لوحة التحكم تعرض أعلى ١٠ نطاقات تكراراً في مجموعتك.

## إجراءات جماعية

بدلاً من حذف/تصحيح رابط تلو الآخر: زرا «نقل كل النتائج الحالية» و«حذف كل النتائج الحالية» يعملان على **كل ما يطابق فلتر البحث/التصنيف الحالي** دفعة واحدة (`POST /links/bulk/delete`، `POST /links/bulk/recategorize`) — مقيّدان بمساحة العمل دائماً.

## البحث: لماذا يختلف السلوك بين التطوير والإنتاج

الإنتاج يستخدم Postgres مع `to_tsvector`، بينما التطوير والاختبارات تستخدم SQLite مع `ILIKE`. هذا الاختلاف أخفى خطأً حقيقياً: محرك Postgres يعامل الرابط كوحدة واحدة (`example.com`، `/python-book.pdf`) فلا يطابق كلمة `python-book` إطلاقاً — أي أن **البحث بجزء من رابط كان يعمل محلياً ويفشل صامتاً في الإنتاج**.

الحل: تقسيم النص إلى كلمات (استبدال كل ما ليس حرفاً/رقماً بمسافة) قبل الفهرسة، وتطبيق نفس التحويل على استعلام المستخدم. العربية لا تتأثر. الفهرس والاستعلام يُبنيان من `app/search.py` نفسه حتى لا ينحرفا، ووظيفة CI مستقلة (`postgres-search`) تشغّل هذا المسار على Postgres حقيقي وتتحقق أن المخطِّط يستخدم فهرس GIN فعلاً.

على Postgres فقط، تُرتَّب نتائج البحث بالصلة (`ts_rank`) لا بالتاريخ فقط — الرابط الذي يتمحور حول كلمة البحث يظهر قبل رابط يذكرها عرضاً ضمن نص طويل. على SQLite (fallback الـILIKE) يبقى الترتيب بالتاريخ لعدم وجود مكافئ حقيقي للصلة.

## التنبيهات

كل تنبيه **يُطفأ على حدة** من «مركز التنبيهات» في اللوحة (`GET /notifications/preferences`).
هذا ليس بنداً من بنود المرحلة بل بوّابتها: نظام تنبيهات تصل مفاتيحه لاحقاً يكون قد
أرسل بالفعل ما لم يُرِده أحد، ولا يُصلح ذلك إعدادٌ يأتي بعده.

| الافتراضي | الأنواع | لماذا |
|---|---|---|
| **مفعَّل** | فشل الجامع، اقتراب حدّ التخزين، دخول من جهاز جديد، نتيجة النسخ الاحتياطي، اقتراب نفاد حصة Groq | الصمت هو العطل الذي وُجدت له: قد تكتشف توقّف الجمع بملاحظة أن مجموعتك توقّفت عن النمو |
| **مطفأ** | الملخّص الأسبوعي، الملخّص الشهري، محتوى البالغين، تصنيف متضارب | ملخّصٌ لم يطلبه أحد هو بالضبط الإرسال الاستباقي |

**كل تنبيه يُسجَّل حتى لو لم يصل** — «انتبه النظام» و«أُبلِغتَ أنت» حقيقتان
مختلفتان، والفجوة بينهما هي المفيدة. والسجل يبقى بعد وضع علامة «مقروء»:
قيمته التدقيقية في أنه لا يُمحى بالإقرار.

**القناة هي البوت** إن كان مربوطاً — الوحيدة المجانية (البريد يحتاج مزوّد SMTP).
والتنبيه يصل إلى **محادثتك أنت** عن **بياناتك أنت**: لا شيء يُرسَل نيابةً عنك إلى طرف ثالث.

**ما يُطلِق كل نوع:**

| النوع | يُطلِقه |
|---|---|
| `collector_failed` | تشغيلة جمع أخفقت فيها كل الحسابات رغم قنوات نشطة |
| `storage_high` | `scripts/check_storage.py` (شهرياً) |
| `new_device` | تسجيل دخول ناجح من عنوان أو متصفّح غير معروف |
| `backup_result` | تقرير تشغيلة النسخ الاحتياطي — **عند النجاح والفشل معاً** |
| `groq_quota` | رؤوس حدّ المعدّل في استجابة Groq، **إن كشفتها** |
| `weekly_digest` | `scripts/weekly_digest.py` (أسبوعياً) |
| `monthly_domains` | `scripts/growth_report.py` (شهرياً) |
| `adult_content` | رابط جديد صنّفه المصنّف ضمن محتوى البالغين |
| `unstable_category` | ثلاثة تصحيحات يدوية على نطاق واحد |

**تنبيه النسخ الاحتياطي يصل عند النجاح أيضاً، وذلك مقصود:** تنبيهٌ لا يصل إلّا
عند الفشل لا يمكن تمييزه عن تنبيه تعطّل — في الحالتين لا يصل شيء. أمّا الوصول
في الحالتين فيجعل **غياب الرسالة نفسه** إشارة: أسبوع بلا رسالة يعني أنّ
التشغيلة لم تعمل أصلاً.

### قناة ثانية اختيارية: webhook تضبطه أنت (الفكرة ١٦٢)

بدل تكامل مستقلّ مع كل خدمة (كلٌّ منها تطبيق OAuth ورمز طرف ثالث مخزَّن وعميل
يُصان)، عنوان `https` واحد تملكه أنت يصل إلى Slack وDiscord وNotion وIFTTT
وغيرها عبر ميزة «الـwebhook الوارد» الموجودة فيها أصلاً — بلا تكلفة وبلا رمز
طرف ثالث تتحمّل هذه المنصّة مسؤوليته.

اضبطه من «مركز التنبيهات ← إرسال التنبيهات إلى webhook خارجي». يصله ما يصلك:
التنبيهات التي تجاوزت المفتاح فقط، وحمولتها `type` و`title` و`body` و`sent_at`
و`source` — **بلا بريدك وبلا معرّفك وبلا أيّ مفتاح**.

**هذا الموضع الوحيد في المشروع الذي تطلب فيه الخدمة عنواناً اختاره مستخدم**، فهذه قواعده:

| القاعدة | لماذا |
|---|---|
| `https` فقط | الحمولة نصّ التنبيه، وهو ما تحميه القاعدة |
| كل عنوان مُحلّ يجب أن يكون عاماً | الداخلي والمحلي وlink-local والمحجوز مرفوضة، والرفض **لا يذكر العنوان** |
| لا يُتَّبع أيّ تحويل | ٣٠٢ إلى عنوان داخلي يُلغي القاعدة السابقة في قفزة |
| لا يُقرأ جسم الاستجابة | يعود رمز الحالة فقط، ومن مضيف عامّ تبلغه أنت بـ`curl` |
| مشفَّر في القاعدة، ولا يُعاد كاملاً أبداً | لا من الواجهة ولا من سجلّ التدقيق ولا من تصدير بياناتك — القناع يُظهر المضيف فقط |
| فشله لا يكلّف التنبيه | التنبيه هو المنتَج، والـwebhook نسخة منه |

**خطر متبقٍّ مذكور:** الفحص يجري قبل الطلب مباشرةً، لكنّ عميل HTTP يحلّ الاسم
مجدّداً بنفسه؛ اسمٌ يتغيّر بين اللحظتين ينفذ من تلك النافذة. غير مُغلَقة عمداً:
من يضبط العنوان مالكُ مساحة العمل، والطلب يحمل نصّ تنبيهه هو، ولا يرى الاستجابة.

**تنبيه حصة Groq مشروط بما لا يمكن لهذا المشروع تأكيده:** الشيفرة تقرأ أيّ
`x-ratelimit-remaining-<بُعد>` مقترناً بحدّه، ولا تفترض اسماً بعينه —
و`console.groq.com` محجوب عن بيئة التطوير فلم يُتحقَّق من الأسماء الفعلية.
غياب هذه الرؤوس يعني صمتاً، لا تحذيراً مختلقاً.

## ترويسات الأمان

| الترويسة | القيمة |
|---|---|
| `Content-Security-Policy` | `default-src 'self'` مع `script-src 'self'` و`style-src 'self'` — **بلا `unsafe-inline` وبلا `unsafe-eval`**، و`object-src 'none'` و`frame-ancestors 'none'` و`base-uri 'none'` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |

**لماذا استغرقت هذه الترويسة عملاً حقيقياً:** سياسة تحمل `'unsafe-inline'`
تسمح بالضبط بما يفعله XSS — أي ترويسة تُقرأ كحماية ولا تحمي. وللوصول إلى
سياسة حقيقية وجب أولاً إخراج **٤٩ معالجاً مضمَّناً** و**خمس كتل سكربت**
و**٢٩ سمة `style`** من الصفحات إلى `app/static/`. النونس لا يحلّ المشكلة:
لا ينطبق على سمة `on*=` إطلاقاً.

المعالجات استُبدلت بـ**تفويض حدث واحد** (`data-action`/`data-args` في
`app/static/app.js`) لا بـ٤٩ مستمعاً: اللوحة تعيد بناء نتائجها عند كل بحث،
فمستمعون لكل عنصر يحتاجون إعادة ربط بعد كل عرض — وعطلها المعتاد زرٌّ
يتوقّف بصمت بعد البحث الثاني.

## حالة النظام والمراقبة

لوحة «حالة النظام» تعرض SHA النشر الحيّ (في تذييل كل صفحة أيضاً)، ورقم
المخطط، وعدّادات هذه العملية، وآخر نتيجة لكل تشغيلة مجدولة.

**اتجاه بيان الاعتماد معكوس عمداً:** قراءة واجهة GitHub Actions من الخدمة كانت
ستتطلّب تخزين **رمز وصول للمستودع** في القاعدة — أقوى من أي شيء آخر فيها. فبدل
ذلك **التشغيلات تُبلِّغ** الخدمة بمفتاح API شخصي لا يستطيع لمس المستودع.

لتفعيلها أضف سرّين في المستودع: `APP_BASE_URL` و`APP_API_KEY` (مفتاح من قسم
«مفاتيح API» في اللوحة). وبدونهما كل شيء يعمل كما هو ولا تصل تقارير فقط.

**العدّادات «منذ إقلاع العملية» لا إجماليات**: الخطة المجانية تنام، فتبدأ من
جديد مع كل استيقاظ — والمدّة معروضة بجانبها كي تكون النافذة مرئية.

دليل الاستجابة للأعطال في **`docs/19-runbook.md`**: من يلاحظ ماذا ومتى، توقّف
كامل، الاستعادة، البدائل إن تعطّلت GitHub Actions، ومؤشّرات مغادرة الطبقة
المجانية.

## نقاط الفحص التشغيلية

- `GET /healthz` — فحص حياة العملية فقط، لا يلمس قاعدة البيانات (حتى لا يعيد Render تشغيل الخدمة بسبب عطل عابر في القاعدة).
- `GET /readyz` — فحص جاهزية حقيقي ينفّذ استعلاماً على القاعدة ويعيد ٥٠٣ إن كانت غير متاحة. يعيد أيضاً `schema_version` (رقم الترحيل المطبَّق فعلاً)، مقروءاً في كل نداء لا مرّة عند الإقلاع.
- `GET /readyz?diagnostics=true` — **يضيف** فحصاً لطبقة Groq الاختيارية ولا يغيّر الجاهزية أبداً: بلا مفتاح يعيد `not_configured` (الوضع الافتراضي، وليس خطأً)، ومع مفتاح يفرّق بين `ok` و`unauthorized` (مفتاح مرفوض، يُصلَح بمفتاح جديد) و`unreachable` (لم يصل الطلب، يُصلَح بالانتظار). اختياري عمداً لأن Render ينادي `/readyz` على جدول: ربط طرف ثالث بالجاهزية يعني أن انقطاعاً عندهم يعيد تشغيل خدمة سليمة. محمي بمهلة ٣ ثوانٍ وتخزين مؤقّت ٦٠ ثانية حتى لا يتحوّل إلى تضخيم طلبات صادرة، ولا يعيد أي جزء من المفتاح.
- `GET /openapi.json` و`/docs` — كل مخطط طلب/استجابة يحمل مثالاً بقيم واقعية، واختبار يعيد تمرير كل مثال عبر نموذجه حتى لا يصير التوثيق كذباً بعد أول تغيير حقل.

## القيود المعروفة (بصراحة كاملة)

- خدمة الويب المجانية على Render "تنام" بعد ١٥ دقيقة خمول، وأول طلب بعدها يتأخر نحو دقيقة (Cold Start) — هذا يشمل أول رسالة تصل للبوت بعد فترة خمول.
- **قاعدة بيانات Render المجانية تُحذف بعد ٣٠ يوماً — وهذا أخطر قيد في المشروع كلّه.** **٣٠ يوماً — مؤكَّد الآن** بلقطة من لوحة Render لنشر حقيقي: قاعدة أُنشئت ٢٣ أغسطس ٢٠٢٦ تحمل «Your database will expire on September 22, 2026. The database will be deleted unless you upgrade to a paid instance type.» وهذا يعني أنّ أرشيفاً يُبنى ليتراكم شهوراً لا يمكن أن يعيش على هذه القاعدة وحدها: إمّا الترقية المدفوعة، أو مزوّد قاعدة آخر بخطة لا تنتهي، أو استعادة يدوية كل شهر. ضع تاريخ الانتهاء في تقويمك يوم النشر. النسخ الاحتياطي الأسبوعي يعمل أسبوعياً بغض النظر عن المدة، لكنه ليس حلاً كاملاً: استعادة القاعدة بعد إعادة إنشائها تتطلب تدخلاً يدوياً (`pg_restore`).
- التصنيف الأساسي (قواعد) يعمل دائماً بدون تكلفة؛ طبقة LLM المجانية (Groq) تحسين اختياري فقط، وتتوقف بأمان دون كسر أي شيء إن انتهت حصتها المجانية أو غابت.
- **عزل الصفوف (RLS) قد لا يعمل إطلاقاً — بصمت — إن كان مستخدم القاعدة خارقاً.** المزوّد المُدار هو من يقرّر أيّ دور تحصل عليه، لا هذا المستودع. `scripts/check_setup.py` يفحص الحالة ويقولها صراحةً؛ لا تفترض الحماية قبل أن تقرأ جوابه. وحتى في أسوأ الحالات لا تسوء الأمور عمّا كانت: الترشيح على مستوى التطبيق قائم ومختبَر كما كان.
- **`links` و`telegram_accounts` خارج RLS.** و`links` أثمن جدول هنا، فاستبعاده كلفة حقيقية لا تفصيلة. السبب مقيس ومكتوب في `app/rls.py`، والطريق إلى ضمّه معه — ولم يُنفَّذ لأنّ قيمته على نشرٍ بمساحة عمل واحدة تقارب الصفر.
- **الترقيم بالإزاحة يتدهور في الأعماق البعيدة:** الصفحة ١٬٠٠٠ تُجاب في ١٨٢ ملّي ثانية، والصفحة ١٠٬٠٠٠ في **١٫٢ ثانية**. تُرك كما هو عن قصد وبقياس (`docs/24-decisions.md` §١٠ و`docs/37`) لأنّ لا سلوك بشري يبلغ الصفحة العشرة آلاف — الرقم مسجَّل كي لا يُكتشَف لاحقاً كمفاجأة.
- **سقف الطلبات المتزامنة التي تلمس القاعدة هو ١٥**، وهو `pool_size + max_overflow` في `app/config.py` — لا حدّ Postgres البالغ ١٠٠. تجاوزه يعطي **٥٠٣ مع `Retry-After`** بعد خمس ثوانٍ، لا انتظاراً طويلاً ثمّ خطأ خادم. السعة اختيار مكتوب، والفشل صريح.
- **خمسة مسارات لا تزال تنفّذ عمل قاعدة على حلقة الأحداث.** جميعها تتطلّب مصادقة ولا يشغّل أيٌّ منها bcrypt، وكلٌّ منها ينتظر إدخال/إخراج شبكياً حقيقياً — لهذا لم تُغيَّر. مذكورة في `ASYNC_BY_DESIGN` داخل `tests/test_event_loop_discipline.py` كي يُجبَر أيّ مسار جديد على تبرير نفسه.
- **كل قياسات الأداء أُجريت على عتاد التطوير لا على Render.** أربعة أنوية هنا، وجزء من نواة هناك؛ فالقيم المطلقة لا تنتقل و**النِّسب هي المُستفاد**. التزامن نفسه مقيس الآن (`docs/39`) بعد أن كان أكبر مجهول: ٤٠ طلباً متوازياً تكلّف **١٥ ميغابايت** إضافية فقط، لكنّ توازي bcrypt المقيس هنا لا وجود له على نواة واحدة.
- **لم يُنشَر هذا المشروع بعد في إنتاج حقيقي.** كل ما سبق تحقّق محلّياً: ٩٥٩ اختباراً، وتشغيل حيّ على PostgreSQL حقيقي. لكن البرود بعد الخمول، وحدّ الحجم، وجدولة GitHub Actions، واتّصال حساب الجمع بتلغرام الحقيقي — لم يُقابَل أيٌّ منها بالواقع.
